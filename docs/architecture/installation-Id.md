# Installation ID

An anonymous UUID that identifies one app installation to the backend. The server uses it
for registration, usage and abuse handling. It is sent as the `X-Installation-Id` header on
every backend request (added in `feat/backend-client`).

## What it is, and what it is not

- A random v4 UUID generated by the app. It is an **identifier, not a secret**, and not authentication.
  Anyone can generate one, so the server never trusts it for access control.
- Not derived from hardware, an advertising ID, an account or any personal data.
- Unrelated to the user's location, which the server receives separately as request parameters.

## Lifecycle

| Event                                         | Result                                   |
|-----------------------------------------------|------------------------------------------|
| First backend request                         | ID is generated and stored               |
| Every later start                             | Same ID is read from storage             |
| Clear app data, or uninstall and reinstall    | New ID, the old one is orphaned          |
| Backup restore or device-to-device transfer   | New ID (the file is excluded)            |
| Storage file corrupt                          | New ID (DataStore corruption handler)    |

The server registers an unknown ID on first sight. There is no registration call and the
app never asks the server whether its ID is known.

## Storage

- `InstallationIdRepository.getOrCreate()` is the only access point.
- Backed by a dedicated DataStore, `files/datastore/installation.preferences_pb`, separate from
  `user_preferences` so it can be excluded from backup without touching user settings.
- Creation is race-free. DataStore serializes `edit`, and the value is only written if none exists.

## Backup exclusion

The file is excluded from Auto Backup and device transfer (`backup_rules.xml` for API 30,
`data_extraction_rules.xml` for API 31+). Without this, a restore would copy the ID to
another device and two installations would share one identity, which breaks per-installation
counting and blocking. This can't be verified by a unit test. When the rules change, repeat the
manual check (`adb shell bmgr backupnow`, reinstall, compare IDs).

## Rules for contributors

- Never log the ID. The HTTP logging interceptor must redact `X-Installation-Id`.
- Don't use it for anything that needs trust, and don't tie it to a user account.
- Don't move it into `user_preferences`.

## Privacy and store listing

- Play Data Safety form: declare "Device or other IDs", collected, not shared, used for app
  functionality and abuse prevention. Update this when `feat/backend-client` ships.
- The privacy policy should say the server stores the ID and a last-seen timestamp. Server-side
  retention is covered by the planned installation cleanup.

## Tests

`InstallationIdRepositoryDataStoreTest` covers first use, stability across calls and instances,
concurrent first calls, and replacement of a corrupt value.
